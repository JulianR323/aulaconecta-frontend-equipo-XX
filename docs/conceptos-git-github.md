 Comprobación conceptual

 1. ¿Qué puede hacer Git aunque GitHub no exista?
Git puede registrar el historial de cambios de un proyecto, crear ramas y realizar commits de forma totalmente local en el computador

 2. ¿Por qué una rama reduce el riesgo de dañar main?
Reduce el riesgo debido a que la rama es un lugar de trabajo similar al main pero en este se puede corregir o desarrollar sin afectar directamente al main.

 3. ¿Qué diferencia existe entre guardar un archivo y crear un commit?
Con un commit tienes el registro de un cambio que realizaste al modificarle algo a un archivo seguido de poder ponerle una nota para identificar ese cambio entre otros commits. Guardar un archivo es sobreescribir el original con la misma información y la nueva sin tener registro alguno de los cambios realizados.

 4. ¿Por qué un pull request no es lo mismo que un merge?
Porque el pull request lanza una solicitud para aplicar o para poder integrar los cambios de una rama en otra. El merge es directamente aplicar los cambios de una rama a otra sin tener que depender de una decisión o solicitud para aplicarlos.

 5. ¿Qué evidencia permite saber quién cambió algo y por qué?
El commit, ya que este se encarga de hacer el correspondiente registro de los cambios realizados en el programa. Este registra el autor y el momento en el que se realizó el cambio, también otros aspectos como el propósito de ese cambio y los archivos modificados.


 Reto rápido de secuencia

Este es el orden en el que se trabaja en GitHub y lo que nos evita cada paso para no meter la pata:

1. Crear repositorio: Es armar la casa o el proyecto desde el principio.
   Riesgo que evita: Empezar a trabajar a lo loco y sin guardar el historial de nada

2. Crear rama: Es hacer una copia aparte para trabajar tranquilos
   Riesgo que evita:Dañar o borrar la versión principal (main) por andar experimentando

3. Hacer commits: Es ir guardando los avances con una nota de qué se hizo
   Riesgo que evita: Que se nos borre un avance o no saber qué fue lo que cambiamos 

4. Abrir pull request:Es avisarle al equipo  ya acabé, mírenlo
   Riesgo que evita: Meter cambios a la versión final sin que los demás sepan

5. Revisar: Es cuando un compañero entra a mirar qué hicimos y si hay errores
   Riesgo que evita:Que se nos pasen embarradas, errores de ortografía o cosas mal hechas

6. Corregir: observaciones: Es arreglar lo que el compañero nos pidió mejorar
   Riesgo que evita: Entregar un trabajo a medias o con mala calidad

7. Fusionar: Es unir el trabajo ya aprobado a la versión final main
   Riesgo que evita: Dejar el trabajo botado en una rama sin unirlo al proyecto Comprobación conceptual
